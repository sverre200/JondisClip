# Microphone audio: investigation and fixes (2026-11-04)

**Complaint:** mic audio in clips "doesn't sound quite right". This report records what was measured, what was found, and what changed. The decisions are in [ADR-0009](../adr/0009-audio-clock-and-mic-processing.md).

## Evidence gathered

### Devices (`audio_probe formats`; only properties are read, no audio)
| Device | Bus | Shared-mode format |
|---|---|---|
| Headset Microphone (Arctis GameBuds) | USB | 48 kHz, 2 ch, float32 |
| Mic/Inst (Samson G-Track Pro) | USB | 48 kHz, 2 ch, float32 |
| **\* CABLE Output (VB-Audio Virtual Cable)**, the Windows default | ROOT (virtual) | 48 kHz, 2 ch, float32 |

- Everything is already 48 kHz float, so the recorder's requested format needs **no resampling or sample-format conversion**. The 44.1 kHz and integer-PCM hypotheses don't apply on this PC. The Arctis mic is USB, not Bluetooth hands-free.
- `settings.toml` has no `microphone_device`, so JondisClip records the **Windows default, which is the virtual cable**, not a physical mic.

### A real clip (DayZ, 40.7 s, 3 tracks; measurements only)
| Track | Peak | RMS | Clipped samples | L/R |
|---|---|---|---|---|
| Mix | −0.1 dBFS | −20.1 dBFS | 0 | stereo |
| Game | −0.2 dBFS | −20.4 dBFS | 0 | stereo |
| Microphone | −2.6 dBFS | −31.3 dBFS | 0 | L = R (mono content) |

- The mic content is real voice, independent of the game (envelope correlation +0.05) and wideband: energy above 8 kHz is −25 dB, above 12 kHz −41 dB.
- **Active speech median −27.4 dBFS**, about 7 dB under the game. The voice sits low in the Mix.
- **The game peaks at −0.2 dBFS**, leaving no headroom, so the old `clamp(game + mic)` hard-clips whenever voice and a loud moment coincide. This clip happened to stay under.
- Single-sample clicks can't be detected *after* AAC (it smears them across 21 ms), so they were measured before encoding (below).

### Device timestamps vs QPC (`audio_probe jitter`, 20 s each)
| Device | Clock drift | Jitter RMS / max | Old corrector actions |
|---|---|---|---|
| CABLE Output | +1 ppm | 0.20 / **1.96 ms** | 0.80 per s |
| Samson | **+28 ppm** | 0.17 / 0.57 ms | 0.35 per s |
| Arctis | +5 ppm | 0.17 / 0.55 ms | 0 |
| Loopback (Arctis headphones) | +5 ppm | 0.19 / 0.63 ms | 0 |

## Root causes
1. **Timing correction damaged the signal (confirmed).** The capture placement nudged by ±1 sample per packet whenever the error exceeded 1 ms. A forward nudge left a one-sample gap that the buffer filled with **zero**, which is an audible click. A backward nudge dropped a sample (a slip). Jitter spikes (the cable) and real drift (the Samson) both triggered it. This affected game audio as well.
2. **Low mic level and no gain control** (confirmed from the clip).
3. **The virtual cable is the default "mic"** (confirmed). Its sound depends on whatever feeds it.
4. **Mix hard-clipping risk** (confirmed: no headroom).
5. **One-sided mics** (USB interfaces with the mic on input 1) would be recorded in one ear. It's not present on these devices, but it's a real failure mode.
6. **Not causes:** resampling, format conversion, bandwidth, Bluetooth, and AAC settings. AAC at 160 kb/s was adequate, but wasteful for a mono voice.

## Before/after: deterministic capture simulation
Test: `audio::tests::capture_timeline_has_no_clicks_or_slips`.
- **Input:** a 440 Hz tone over 60 s, sent as 480-frame packets with the measured drift and jitter profiles, through the real placement code, buffer and mixer reads.
- **Glitch:** any sample deviating more than 0.2 % of amplitude from a smooth sinusoid.

| Profile | Before | After |
|---|---|---|
| Virtual cable (jitter spikes) | 172 glitches (2.9/s), worst 0.058 | **0**, worst 0.0001 |
| Samson (28 ppm) | 142 (2.4/s), worst **1.92** (inserted zeros, full-scale clicks) | **0**, worst 0.0001 |
| Arctis (5 ppm) | 6 (0.1/s) | **0** |

"Worst 0.0001" is the resampler's precision, −80 dB relative to the signal.

## Review (perf-reviewer) and fixes
Every issue below was fixed and is covered by a test:
- **Negative first pts** on limited tracks (it would shift the first TS segment). The mixer now starts at `BLOCK + LIMIT_DELAY`.
- **3-packet wait on large forward jumps.** It now restarts at once above 100 ms.
- **Limiter sliding-min deque overflow on loud bass.** It now expires entries before pushing, and matches a brute-force reference at 20/30/50 Hz.
- **Meter error hidden and a thread respawning every 100 ms.** The error is now kept, with a 1.5 s retry backoff.
- **Meter fold differed from the recorder's** for one-sided mics. It now uses the same rule.
- **Smaller fixes:**
  - Resampling now runs outside the buffer lock, and the filter table is built ahead of time.
  - Phase interpolation keeps the off-unity error under 2×10⁻⁴.
  - MonoFold has hysteresis and recovers from NaN.
  - The limiters reset on mixer skip-ahead.
  - The drift cap is raised to 1000 ppm.

## Overhead (`record` example, 1080p60, Mix/Game/Microphone tracks)
- Before (earlier run): 0.66 % CPU, 74 MB.
- After: 0.48 % CPU, 73 MB. That's within run-to-run noise, so **no measurable regression**.
- Resampler cost: 16 multiply-adds per sample per channel, about 3 M per second for two sources.
- The UI level meter runs only while the settings window shows the mic section, in the UI process.

## A/V sync after the change (screen unlocked, about 700 captured frames per run)
Flash/beep test: a 640×360 always-on-top window, a 1 kHz beep of 100 ms each second, and the mic enabled (Mix, Game and Microphone tracks).

| Run | Mix offset (median, range) | Game offset (median, range) |
|---|---|---|
| 1 | −4.3 ms (−14 to +6) | −8.0 ms (−13 to +7) |
| 2 | −4.3 ms (−31 to +6) | −8.0 ms (−30 to +2) |
| 3 | −4.3 ms (−14 to +22) | −3.0 ms (−13 to +19) |

- All runs are within the ±40 ms target and comparable to the pre-change runs earlier the same day (+4 and −18.5 ms). The test resolution is 5 ms (audio windows) and 16.7 ms (video frames).
- **Mix vs Game alignment, sample-accurate:** cross-correlation peaks at exactly −63 samples. Each track is decoded from its own first packet, and the Mix starts 63 samples earlier by design, so that peak means the content is **exactly aligned**: the limiter's 63-frame delay is compensated correctly.

## Not verified here
- **Listening.** No subjective claim is made, and only signal measurements were taken.
- **Early A/V runs while the PC was locked are invalid.** Windows produced no new screen frames, so the video was effectively frozen (14 distinct frames out of 391) for old and new builds alike. They're superseded by the unlocked runs above.
- **Real mono-only or one-sided USB interfaces.** Covered by unit tests only.
